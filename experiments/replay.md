# 回放分析：如果当时有归因层，会得出什么结论

数据来源：`experiments/records.jsonl`（21 条，E01–E21，来自 HANDOFF.md）。

## 数据质量先说明
- 只有 E04、E05、E12、E18 同时记录了 wall 与 device 或 host 分解。其余 17 条只有 makespan 或正确性，归因层无法从它们推断瓶颈。
- 多数 `wall_s` 是单对测量（`single_pair`）或不同代码版本的比较（E07 vs E01、E06 早期结果），属于 `evidence_quality` 为 low 或 medium 的记录。
- **结论：当前历史数据足以检验归因规则的方向，但不足以统计验证阈值。** 这正是硬件探针要补的部分。

## 逐条回放（归因层会做什么，实际发生了什么）

## 对归因层设计的三条修正
1. **设备时间不能替代 wall 时间。** 任何声称"减少设备时间"的假设，都必须同时预测 wall 变化，否则不接受。
2. **诊断先于改动。** E07/E08 和 E04 显示，计数器和包装器计时能便宜地排除方向。归因层应先提出可证伪的诊断，只有诊断支持时才动代码。
3. **每个实验要有可加和的分解。** 总时间应拆成：prefill、decode 每步时间、decode 步数、准备时间。E19 说明没有步数会误判。

## 第一版硬件探针需求清单（由上面的缺口推出）
1. **派发与同步**：单步 host 派发时间、同步次数、同步阻塞时间（用 wall 测，不只用 profiler）。
2. **设备忙碌率**：device 时间并集 / wall 时间，用于验证 E05 类的 mismatch。
3. **算子级成本曲线**：matmul 在相关 shape 上的吞吐；conv1d 与逐元素实现的对比（用于 E02、E05 类问题的预测）。
4. **图捕获开销与收益**：捕获时间、replay 时间、不同 bucket 大小下的 padding 成本（E12、E15）。
5. **显存**：权重、KV、状态的占用；预留给 prefill 的瞬时峰值；分配器碎片测试（E09、E14）。
6. **集合通信**：all_reduce 的延迟与在图内外的成本（E20）。
7. **调度模型**：解码步数随 slot 数与请求长度的变化，用于预测步数（E07、E19）。
