Gemma · Qwen 优化路线

两个模型用同一套方法：先 profile 找瓶颈，每次只改一处，用 ABBA 交替测量来确认收益。Qwen3.5-27B 的主要收益来自连续批处理、GDN 的 chunk 化与 NPUGraph；Gemma-4-26B-A4B 没有 GDN，也无法稳定捕获图，主要收益来自减少 MoE 与 norm 的小算子派发。

8365 → 410 s
Qwen3.5-27B · 串行基线到当前最优（约 20×），正确数 116 → 118 / 128
10589 → 661 s
Gemma-4-26B-A4B · 串行基线到当前最优（约 16×），正确数 108 → 110 / 128（fresh-v1）

方法：每一步都是同一个循环

  1. 1 · Profile分开测 wall 与 device，分解到 attention、experts、router、norm 等段。
  2. 2 · 提出可证伪假设写明预期方向与幅度，例如“每步 device 时间降 23%，wall 应随之下降”。
  3. 3 · 单一改动一次只加一个 flag，代码默认关闭，直到通过测量。
  4. 4 · ABBA 测量交替运行 A、B、B、A。收益需 ≥2%，且两组区间不重叠。
  5. 5 · 正确性门控正确数不降、无丢题；文本变化须单独解释（bf16 舍入 或 逻辑错误）。

失败也记录：device 时间降了但 wall 不变（Qwen E05），或 wall 变快但正确数崩掉（Gemma E-G36），都会被否决。

两条路线

Qwen3.5-27B GDN + 图

瓶颈随阶段转移：先 batch 浪费，再 prefill 里的 GDN，最后 decode 的 host 与卷积。

    串行 B=1 HF 基线
    8365 s · 116/128
  2. 1
    batch16 + 融合算子采纳
    串行逐题浪费大量算力
    1180 s · 116/128
  3. 2
    自写连续批处理 CBEngine（slot 制）采纳
    静态 batch 中已完成的行仍在算，约 53% 行·步浪费

Gemma-4-26B-A4B MoE + 派发

没有 GDN，也没有 conv。单步有 3442 个算子，99% 的时间在 enqueue，瓶颈是派发，不是 device 算力。
  1. 0
    串行 B=1 基线（gemma_run.py，无 flags）基线
    10589 s · 108/128（fresh-v1）
  2. 1
    弃用手写 decode 循环否决
    手写循环每步比 generate() 慢约 2×，原先“派发占 99.7%”的结论作废
  3. 2
    融合 RMSNorm（--fast-norm）采纳
    逐层 profile：7 个 norm 合计约 32%，单次 norm 247 → 49 µs
    ABBA 1346 → 990 s，−26%（first16）
  4. 3
    连续批处理 CBEngine（--cb --slots 16）采纳
    自写 attention；MoE、norm、router 复用 HF。初次默认路径 770 s，比 Qwen 慢，暂停，之后继续优化
    770 s · 14/16（first16）
  5. 4
    计数器探针：每步固定成本主导诊断
    真实循环每步约 750–830 ms，几乎不随活跃 slot 数变化；每步 3442 个算子，enqueue 占 99%
  6. 5
    只算活跃行（--compact）采纳
    ABBA 793 → 672 s，−15%（first16），13/16
  7. 6
    分组 experts（--grouped-experts）采纳
    experts 占 decode 的 55%，每层约 22 个不同 expert 被激活
    ABBA 690 → 368 s，−47%（first16），12/16 不变

    noscale norm + 融合 RoPE（--fast-norm-noscale --fused-rope）采纳

    ABBA 243 → 197 s，−19%（first16），13/16 不变；叠加 fast-norm 时为 −34%

    prefill 的 MoE 层替换为分组实现；单层数值差 ≤0.001

当前最优配置

Qwen3.5-27B：410.0 s · 118/128

CBEngine + fast-GDN v1 + GDN v2 + graph decode + elem-conv，prefill 分组 pg1，需要 expandable_segments。

Gemma-4-26B-A4B：661.5 s · 110/128（full128，ABBA 的 B 组）

--cb --slots 16 --compact --grouped-experts --fast-norm --fast-norm-noscale --fused-rope --prefill-grouped

失败的分支（同样记录）

Qwen

  • shift-conv：被 elem-conv 取代
  • sync-free：ABBA 慢 4%，同步计数不能预测 wall 收益
  • 24 slots：显存 OOM
  • graph bucket 128：增益 0.9%，低于门槛
  • E18 规则“replay ≈ device 和 ⇒ device-bound”：被 E04 推翻

Gemma

  • NPUGraph 不可用：回放是静默 no-op，输出与 eager 不一致（两套环境均复现）
  • fia + geglu：正确数 12 → 1/16，wall 降低是因为输出被破坏
  • router fused：慢 47%，且正确题集合变化
  • slice-kv：慢 6%；nocopy：−1%，在噪声内
  • host-tact：中位数降 3%，但区间重叠，暂不采纳

如何解读这些数字

  • 两个模型的评测协议不同（SYSTEM 与 USER_SUFFIX 不同），绝对秒数不能跨模型直接比较。
  • Gemma 的 10589 s 基线与最终 661 s 不在同一次 ABBA 里，倍数是跨会话估计。可直接引用的是 ABBA 内的配对收益。
  • Gemma 的正确数用 fresh-v1 评分；早期 agent_protocol 的 106/128 已弃用。
  • Gemma 的多数 ABBA 只在 first16 上做过；full128 上只验证了 prefill 分组。
  • “正确数持平”与“文本逐字一致”是两件事。bf16 舍入会改变生成路径，因此每次都要看正确题集合是否变化。
