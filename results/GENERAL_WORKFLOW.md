# 通用端到端推理优化 workflow

来源：两个案例。
- 910B（本仓库）：串行基线 8365 s（128 题）→ 410 s（118/128）。
- H100（`/remote-home/S45160/work/e2e_acceleration_by_claude`）：1470.6 s（127 题）→ 8.36 s（0.945）。

H100 Ascend 报告不作为依据。两个案例的数字口径不同（910B 为 128 题，H100 为 127 题），比较时要标注。

workflow 的目标：给定一张卡、一个模型，以及**用户自己的 agent 负载**，按固定顺序做测量与决策，而不是照搬某张卡的优化顺序。

工具本身不附带数据集。用户提供自己的负载（请求集合、工具定义、解码规则）；工具只负责测量与决策。两个案例的 GSM8K 只是各自的评测负载，不是工具的输入约定。

---

## 阶段 0：固定口径（必须先做）

1. **负载来源**：用户可以提供自己的负载（请求集合、prompt、解码规则、工具定义），也可以不提供，直接使用工具内置的默认负载。两种情况下，工具都记录输入的指纹（哈希），保证同一次比较使用同一批输入。

   **默认负载（与两个优化案例相同的设置）**：
   - 数据：GSM8K 128 题，文件 `data/benchmarks/gsm8k_128.jsonl`（sha256 `8ad965a8…b471fae4`，共 128 行，每行含 `id`、`question`、`answer`）。这是 910B 案例使用的同一个文件。
   - 解码：greedy（`do_sample=False`），non-thinking 模式。
   - 轮数与长度：第一轮最多 512 token，之后每轮最多 512 token（`--final-max-new-tokens` 默认 512），最多 6 轮。
   - 工具：python 工具，在子进程中运行，超时 10 s；工具调用格式为 Qwen 原生格式。
   - 模型：Qwen3.5-27B（默认设置；换模型时工具需要重新确认工具调用格式）。
   - 判分：答案与 `answer` 字段比较，因此默认负载会报告 accuracy 与正确集合。
   - 注意：两个案例的 makespan 口径不同。910B 结果为 128 题；H100 结果排除了 task 423（127 题）。默认负载的报告按 128 题输出，若要与 H100 对齐，需要在报告中标注“排除 task 423”的结果。task 423 不会被工具自动排除。
   - 默认负载的指纹（数据文件哈希与解码参数）写入 `baseline.json`。
2. **不丢弃请求**：工具不得因为某个请求耗时长、答错或复读就把它排除出测量。所有请求都计入 makespan 和 accuracy。两个案例里 task 423 的排除只是为了和历史口径对齐，是报告层面的做法，不属于优化流程。
3. **指标**：主指标是 makespan（整批墙钟）。护栏是 accuracy 与正确集合（若用户提供了判分方式）。辅助指标是各部分耗时占比、turns、tool calls、tokens，以及尾部分布（P50 / P90 / max 的请求耗时）。
4. **基线**：串行、最简单的实现，作为工具内置的参照。记录 makespan、accuracy（如有）、per-request 结果。

产出：一个 `baseline.json`，包含输入指纹、解码参数、makespan、尾部分布、正确集合（如有）、硬件与软件栈版本。

## 阶段 1：测量方法（先于任何优化）

来自两个案例的经验：噪声大于信号时，优化结论不可靠。

- **墙钟优先**：用墙钟 step 或 makespan 判断效果，profiler 的 device 时间只作诊断。
- **同卡 ABBA**：交替运行 A、B、B、A 等，两组范围不重叠才算有效。910B 的噪声约 ±10 s，小于 2% 的收益无法判断。
- **正确集合**：逐题比较正确集合，不只比总数。
- **确定性检查**：同配置重复运行，看 final_text 是否一致。若不一致，标注为数值改动，并把它单独归类。
- **replay 模式**：当轨迹不确定时，强制使用已记录的 token 轨迹做计时对比（H100 的 `--replay`）。
- **同一时段对比**：不同时间段的集群负载会改变绝对值，只比较同批次运行。

门控：收益 < 2% 且噪声范围内 → 不接受。

## 阶段 2：测量瓶颈类型（核心决策）

在做任何优化前，先回答：时间花在哪里？

| 探针 | 测什么 | 判读 |
|---|---|---|
| 时间分解 | prefill / decode / 工具 / 调度空闲 的占比 | 找到占比最大的部分 |
| 成本驱动因素 | 成本是随 token 数增长，还是随调用次数增长 | 调用次数主导 → 减少 eager 调用、host 同步、launch；token 主导 → kernel、GEMM |
| 派发 vs 设备 | 设备忙碌比例（GPU/NPU busy）或 device 时间和与墙钟的差距 | 差距大 → launch / host 受限；差距小 → device 受限 |
| 功耗 / 频率 | 大 GEMM 下的频率、功率 | 撞功耗墙 → 微基准结论可能失效 |
| 理论下限（SOL） | 权重字节 / 带宽 + 每 token 状态字节 / 带宽 | 估出下限，判断剩余空间 |
| 关键路径 | 最长的 agent 链（串行轮数）与单步平均时间 | 批处理后，关键路径决定 makespan；这是对用户负载的测量，不是删除请求 |

两个案例的反例都说明：**不能预设瓶颈类型**。
- 910B：decode 受 host 派发限制。
- H100：decode 在大 batch 下受功耗墙限制，同时 prefix reuse 减少 89% token 但收益为 0，因为成本在调用次数。

## 阶段 3：按瓶颈选择候选

每个候选在做之前，要先写清楚：前置条件、预期收益及依据、门控、对应的探针。

### 3a. 调度层（通常收益最大，先做）

- **连续批处理 + slot 状态**：910B 约 1.6×（1180 → 755 s），H100 7.8×（474.8 → 60.8 s）。
  - 前置：KV、循环状态（recurrent / conv state）能按 slot 管理。
  - 显存决定 slot 上限：权重、KV、状态预算算清楚。910B 为 16 slot（24 OOM），H100 为 64 slot。
- **异步工具执行、suspend/resume**：H100 Phase 2 中工具占 17.7%，且阻塞所有行，改为异步后有收益。
- **chunked prefill 与 decode 混合 step**：H100 引擎重写的一部分。

### 3b. 派发层（host 受限时）

- **graph 捕获 decode 步**：前置是静态 shape（按长度分 bucket）、静态输入缓冲、共享内存池、预先捕获后再 prefill。
  - 910B：NPU Graph 有效，588 → 500 s。
  - H100：StaticCache + CUDA graph，1673.6 → 660.8 s（2.5×，含 task 423）。
- **减少 eager 调用次数**：把短 suffix 当作 forced token 走 decode graph（H100 p2_s03、p2_s10）。
- **去掉 host 同步**：先统计 `aten::_local_scalar_dense` 等计数，确认是瓶颈再做。同步次数高不等于它是瓶颈，需要用门控验证。
- **allocator 配置**：图模式下 prefill 可能 OOM，需要可扩展段之类的设置。

### 3c. Kernel 层（device 受限时，或架构改动之后）

- **替换回退路径**：用专用 GDN / 线性注意力 kernel 替代 torch 参考实现。910B 同代码 A/B 约 −22%。
- **状态无关计算批量预计算**：910B GDN v2，prefill −19%。
- **融合**：RMSNorm、silu_mul_quant、GDN 递推与输出。H100 中 GDN 融合持续有效。
- **低精度 GEMM**：H100 FP8 per-tensor，28.6 s 阶段约 1.25×。需要端到端精度验证，并检查不同长度（longctx）下的稳定性。
- **GEMM 库 vs 自写 kernel**：先测库（cuBLAS / ACLNN）的速度，自写 kernel 只有在不比库慢时才值得做。H100 中精确累加 FP8 GEMM 上 Triton / CUTLASS 追不上 cuBLAS。
- **递减信号**：架构改动之后，单项 kernel 改动收益 <1% 时即到墙，此时应停止。

### 3d. 不在阶段内的方向

- **prefix / 状态复用**：先确认成本驱动因素。token 减少不代表时间减少。
- **算子改写（卷积等）**：结果可能不同，需要先做正确集合比较（elem-conv 的 final_text 与非 elem 不一致，待补做）。
- **投机解码、MTP**：改变了优化对象，两个案例都明确排除在通用 workflow 之外，单独记录。

## 阶段 4：验证与门控（每个候选必须通过）

1. **单元正确性**：算子或模块与参考实现逐位或在容差内一致。
2. **小规模端到端**：16 题或同等规模，检查 accuracy、turns、tool calls、tokens。
3. **全量 ABBA**：全量负载，同卡交替，不重叠才接受。
4. **长上下文 / 泛化**：H100 中 tf32 求逆在随机输入和 127 题上正常，却让 longctx 从 0.94 跌到 0.417。因此还需要病态输入与长上下文测试。
5. **数值改动标注**：非 bit-exact 的改动单独标注，并做正确集合比较。

门控规则：
- 收益 < 2% 且在噪声内 → 拒绝。
- accuracy 下降超过噪声 → 拒绝。
- 正确集合变化 → 需要逐题分析后再决定。

## 阶段 5：停止与记录

- **停止条件**：最近几个候选的收益都 <1%，且理论下限（SOL）的剩余空间小。H100 在此时约达 SOL 的 85%。
- **记录**：每个候选写入注册表，字段为 `id`、`name`、`preconditions`、`probe`、`expected_gain`、`gate`、`status`（accepted / rejected / unverified）、`stack`（驱动、CANN/CUDA、框架版本）、`evidence`（结果目录）。
- **否决项同样入库**：每条记录写明候选、测量结果、拒绝原因，并带上硬件与软件栈标签。否决结论只在对应的卡与栈上成立，换卡后可以重新测。框架不预置任何具体的否决项。

## 阶段 6：迁移到新卡

1. 固定负载与口径（阶段 0）。
2. 跑基线与探针（阶段 1–2）。
3. 按探针结果选择候选（阶段 3），而不是照搬其他卡的顺序。
4. 阶段 4 的门控全部通过后才接受。
5. 记录到注册表（阶段 5）。

## 一页版

```
固定口径 → 基线 → 测量方法（ABBA、正确集合、确定性）
  → 探针（时间分解、调用次数 vs token、派发 vs 设备、功耗、SOL、关键路径）
  → 按瓶颈选候选：调度 > 派发（graph、减调用） > kernel（回退路径、融合、低精度）
  → 每个候选：单元 → 小规模 → 全量 ABBA → 长上下文
  → 收益 <2% 或 accuracy 下降则拒绝
  → 连续多个候选 <1% 且接近 SOL → 停止
  → 记录（接受与否决都入注册表）
```

## 局限

- 两个案例都是同一类模型（Qwen3.5-27B，混合 GDN + 全注意力）和同一类负载（GSM8K 工具 agent，greedy）。通用性需要第三个模型或负载来验证。
- 910B 的数字是 128 题口径，H100 是 127 题口径，比较时要标注。
- AMD 尚无案例，本 workflow 对 AMD 只是假设。
- 910B 的 410 s 最优结果目前缺少 127 题的重跑。
